# On screen visuals and explainers (research, 13 Nov 2026, fact checked)

Read only research. Fact check pass on 13 Nov 2026: every source below was reopened (raw files fetched, GitHub API read, sizes re measured). Changes from the first draft are listed at the end. Anything still not confirmed is marked **unconfirmed**.

## The short answer

- **Are we doing something like this already?** Partly, and more than the first draft said. Squibby's overlay already draws hand made marks (ring, arrow, underline, box) as SVG in a panel that ignores the mouse, and it already has "Draw it for me": a small "why did this break" diagram built from the project and the failing place (never the screen), laid out by a deterministic left to right layered layout in `layout.ts`. What it does not have is HeyClicky's **draw and explain** stage: a drawing that builds stroke by stroke in time with the spoken answer, labels that move apart, and turnable 3D models. (Seen in `app/src/overlay.ts`, `marks.ts`, `sketch.ts`, `layout.ts`, `commands.ts` line 110, in the worktree `.claude/worktrees/agent-ad1481be1b6c65dab`, last commit 22 Oct 2026. `git log --all` shows no newer commit in this repo; the newer milestones in the founder's notes must live elsewhere, so the current app may already differ. **Unconfirmed** for anything after 22 Oct.)
- **How HeyClicky does it:** unknown in detail, because HeyClicky's new code is private (Farza's own README note, 27 April 2026). The best public description of the technique is OpenClicky (MIT), which says its stage is "the same kind of feature HeyClicky ships": the model writes a tiny drawing program, a sandboxed web page runs it statement by statement as it streams and paints SVG strokes, with 3D parts in three.js. That HeyClicky works the same way inside is an inference, **unconfirmed**.
- **HeyClicky is a YC company** (Spring 2026, primary partner Aaron Epstein) and already lives in the Mac notch, drives Mac apps, runs agents and draws in 2D and 3D. A YC partner will ask why Squibby is not a feature of HeyClicky. The answer has to be: Squibby is about **proving and undoing what coding agents changed**, which HeyClicky's pages do not mention at all.
- **The reel** is a video editor selling SaaS explainer videos. The useful idea for Squibby: show a change as a short animated story, not as text.
- **Recommendation:** (1) an animated "what changed" replay for every review, (2) a living "how your app fits together" map (largely an extension of the existing Draw it for me layout), (3) a 60 second explainer rendered from code. All three reuse the SVG pen Squibby has. Add three.js only if a test shows people want 3D. None of this has user evidence yet; see "Questions a YC partner will ask".

## 1. How HeyClicky / Clicky draws on the screen

### 1a. The open source original (farzaa/clicky): pointing only

- MIT, 8,005 stars and 1,604 forks, last push 28 Oct 2026 (GitHub API, read 13 Nov 2026). https://github.com/farzaa/clicky
- The README's "Update: April 27, 2026" from Farza: the existing code stays open source, "for all the new stuff I'm hacking on, gonna keep it private". (First draft cited a third party page for this; the primary source is the README itself.) https://raw.githubusercontent.com/farzaa/clicky/main/README.md
- **The overlay window** (`leanring-buddy/OverlayWindow.swift`, checked line by line): `class OverlayWindow: NSWindow`, `.borderless`, `isOpaque = false`, `backgroundColor = .clear`, `level = .screenSaver`, `ignoresMouseEvents = true`, `collectionBehavior = [.canJoinAllSpaces, .stationary, .fullScreenAuxiliary]`, `canBecomeKey` and `canBecomeMain` overridden, content in an `NSHostingView`. https://raw.githubusercontent.com/farzaa/clicky/main/leanring-buddy/OverlayWindow.swift
- **The pointer** is a blue glowing SwiftUI triangle. It follows the mouse with `.spring(response: 0.2, dampingFraction: 0.6)`, polled by a 0.016 s `Timer`. To point it flies a **quadratic bezier**: control point above the midpoint by `min(distance * 0.2, 80)`, flight time `distance / 800` clamped to 0.6 to 1.4 s, a 1/60 s timer per frame, rotated to the curve's tangent with `atan2`. A bubble streams the phrase one character at a time with a scale in from 0.5. Same file.
- **Finding where to point** (`ElementLocationDetector.swift`): the screenshot goes to Claude with the Computer Use tool defined, because per the code comment it "activates Claude's specialized pixel-counting training". It picks 1024x768, 1280x800 or 1366x768 by aspect ratio, reads back the coordinate, clamps it and scales it to screen points. https://raw.githubusercontent.com/farzaa/clicky/main/leanring-buddy/ElementLocationDetector.swift
- The README describes `[POINT:x,y:label:screenN]` tags in the streamed reply and a Cloudflare Worker proxying the Anthropic, AssemblyAI and ElevenLabs keys. Same README.
- **Keeping its own windows out of screenshots:** `CompanionScreenCaptureUtility.swift` uses ScreenCaptureKit's `SCContentFilter(display:excludingWindows:)` with the app's own windows. https://raw.githubusercontent.com/farzaa/clicky/main/leanring-buddy/CompanionScreenCaptureUtility.swift
- **Not in the open repo:** labels on leader lines, diagrams or 3D.

### 1c. How it can be built: OpenClicky's "draw stage" (MIT, clean room)

OpenClicky: MIT, 52 stars, 19 forks, created 3 Sep 2026, last push 9 Nov 2026 (GitHub API). Its draw stage doc says it is "the same kind of feature HeyClicky ships as 'draw and explain'", written from scratch with "no HeyClicky code, prompts or assets". Important nuance missed in the first draft: the shipped stage is in OpenClicky's **Windows** app (WebView2, PR #39); the **Mac** version is a design spec dated 4 Nov 2026, not confirmed as shipped. https://github.com/prasanthsasikumar/openclicky , https://raw.githubusercontent.com/prasanthsasikumar/openclicky/HEAD/docs/draw-stage.md , https://raw.githubusercontent.com/prasanthsasikumar/openclicky/HEAD/draw-stage/README.md

How it works (all checked against those two files):

1. **The model writes a program, not a picture:** beats of `step` + `say`, then calls such as `rect`, `circle`, `arrow`, `text`, `card`, `photo`, `chart`, `timeline`, `figure`. Coordinates are in "canvas units", the screenshot the model saw, "usually 1280 wide"; the page scales them.
2. **It draws while it streams.** A statement ends at `;`, a line break or `}` outside brackets, strings and comments, and runs in a sandboxed worker (`stage-worker.js`) with network and worker APIs removed.
3. **Timing:** each beat's strokes run "up to about 3x faster or 2x slower than its natural speed" to finish with the spoken line; the default clock gives each line "word count / 2.6 seconds".
4. **Labels keep apart:** a label that would land on another "moves the least it can, up or down before sideways"; chart labels take the spot that crosses the fewest strokes; timeline labels take the shortest free stem.
5. **3D** is `figure3d.js` on three.js r172. Parts: lathe, extrude, tube, spring, gear, organic `blob` (a distance field meshed with surface nets), materials from steel to pcb, `cut` for cutaways, motion `.spin .bob .pulse .orbit .move`. Look: soft key light with shadows, rim light, ink outline, "labels as small tags on leader lines that keep to their side and their order while the figure sways". A clicked part is asked about by name.
6. **Detail and cost settings:** simple 8 to 15 parts and 3 to 4 beats, detailed 15 to 40 parts, very detailed 30 to 70 parts and up to 7 beats "with 16,000 tokens to write them". (New in this pass.)
7. **Mac window (spec only):** a borderless non activating `NSPanel` over the cursor's screen, level `.statusBar`, `ignoresMouseEvents = true` by default, a `WKWebView` with `drawsBackground` off, a custom `openclicky-stage://` scheme with CSP `'self'` and `connect-src 'none'`; mouse events turn on only while the pointer is inside a card, figure, button or grip; the window and page are prepared when the talk key goes down. https://raw.githubusercontent.com/prasanthsasikumar/openclicky/HEAD/docs/superpowers/specs/2026-11-04-draw-and-explain-mac-design.md
8. **Cost per drawing (OpenClicky's own budget, not a general rule):** the spec raises its backend's 1,024 token cap to 8,192 for drawings and says that "costs an account roughly eight ordinary answers of budget". The model is first asked to reply `NONE` unless a drawing is genuinely needed; `NONE` costs "one short extra round-trip". Same spec.

**What this means for Squibby:** Squibby's overlay is already the same shape (SVG in a page whose panel ignores the mouse and never takes the keyboard, per the header of `overlay.ts`). The gap is the drawing language, the timing and label layout, not the window. OpenClicky's work is MIT and can be studied or adapted with attribution; HeyClicky's code is private and must not be copied.

## 3. What runs well in a transparent overlay on a Mac, and what it costs

| Technique | Good for | Cost and limits | Source |
|---|---|---|---|
| **SVG in a web view (what Squibby has)** | Hand drawn strokes, labels, boxes and arrows; "draw on" by animating `stroke-dashoffset` | Already shipped, so near zero new cost. Optional: Rough.js 4.6.6 bundled ESM 27,748 bytes raw / about 8.9 KB gzip; perfect-freehand 1.2.2 3,770 bytes / about 1.8 KB (re measured 13 Nov 2026). Squibby's own `sketch.ts` already does the wobbly pen, so neither is needed | https://cdn.jsdelivr.net/npm/roughjs@4.6.6/bundled/rough.esm.js , https://cdn.jsdelivr.net/npm/perfect-freehand@1.2.2/dist/esm/index.mjs |
| **three.js (WebGL) in the same web view** | Turnable 3D models with labels on leader lines | three.js r172 needs both `three.module.min.js` (339,437 bytes / about 79 KB gzip) and `three.core.min.js` (366,322 / about 96 KB): about **705 KB raw, 175 KB gzip together** (re measured). MIT. Needs mouse events on the model only | https://cdn.jsdelivr.net/npm/three@0.172.0/build/three.module.min.js , https://cdn.jsdelivr.net/npm/three@0.172.0/build/three.core.min.js |
| **SwiftUI in an `NSHostingView`** | Pointer flight, springs, bubbles (Clicky's approach) | Native and smooth, but Squibby is Tauri + React, so more Swift beside the Rust shell | Clicky `OverlayWindow.swift` above |
| **Core Animation (`CAShapeLayer` + `strokeEnd`)** | Cheapest "draw the line on" animation | Native only. The Apple page did not render; detail is from general knowledge (**unconfirmed in this session**) | https://developer.apple.com/documentation/quartzcore/cashapelayer/strokeend |
| **Tauri transparent windows** | Squibby's host | Tauri's config reference: `macOSPrivateApi` "enables the transparent background API" and is a "No-op in Tauri 2.12.1+ because the APIs are always enabled now". Squibby pins `tauri = "=2.12.1"` and still sets `macOSPrivateApi: true`, which is now harmless but dead | https://v2.tauri.app/reference/config/ |

**Not measured (unconfirmed):** memory and CPU of a second always ready WKWebView, and frame rate of a three.js figure over a full screen video. Needs a short spike on a real Mac first (AGENTS.md rule 18).

**Hiding the overlay from screenshots.** Clicky excludes its own windows with ScreenCaptureKit's `SCContentFilter(display:excludingWindows:)` (file linked in 1a), and OpenClicky's spec relies on the same utility. Do that, not `NSWindow.sharingType = .none` alone; I could not read Apple's page, and whether ScreenCaptureKit honours `sharingType` on macOS 27 is **unconfirmed**. https://developer.apple.com/documentation/appkit/nswindow/sharingtype-swift.property

**Squibby's own rules still apply:** drawing only on a user hotkey or for a review the user opened (AGENTS.md rule 5), the panel never takes focus (rule 9), drawings clipped to the confirmed window and cleared when it changes (F17 rule 22, cited in `spikes/draw-overlay/RESULTS.md`), and Stop everything clears them (rule 11).

## 4. Recommended: the three most useful visual features

### Feature 1: "Watch what changed", an animated replay of every review (build first)

**Why:** Squibby's core job (a plain words review plus proof) made visible. In the HeyClicky pages and release notes I read, drawing is used to teach and explain, never to review code changes. That "no competitor does it" is only true of what I checked here; the separate competitors file should be the source for any wider claim.

**How to build it:**
1. Reuse the idea, not the code: a small safe drawing language (`step`, `say`, `box`, `arrow`, `label`, `highlight`, `tick`, `shot`), run in a Web Worker in the existing overlay page. Strict CSP, no network.
2. The model never invents facts. The runner builds a fact sheet (files changed from the shadow snapshot diff, which part of the app each belongs to, checks with exit codes, the proof screenshot path). The model only arranges it into 3 to 6 beats. A validator rejects any beat naming a file, check or result not in the sheet (rule 14, "done means proven").
3. Draw with the existing `sketch.ts` pen; animate `stroke-dashoffset`; spread each beat over its line (word count / 2.6 s when silent, the voice's start and end events with voice on).
4. Labels: add the "move the least, up or down before sideways, keep order, drag the arrow" rule to the existing `layout.ts` (which already has `fitLabel` and `wrapLines`), tests first.
5. Show a small playing thumbnail in the review card on the notch hover panel; full size on the screen on "Watch". Undo and the receipt sit under it.
6. Settings: replay on or off, speed, reduce motion (static diagram), voice on or off.

**Cost:** 1 extra model call per review with capped output. Start near 2,000 tokens; whether that is enough is **unconfirmed** (OpenClicky's detailed drawings use up to 8,192, but they draw machines, not 3 to 6 boxes). No new libraries.

### Feature 2: "How your app fits together", a living map

**Why:** non engineers lose track of what their AI built. A map that lights up the changed part serves "where was I" (job 3) and "explain" (job 4), and makes a strong screenshot.

**How to build it:** this is mostly an extension of Draw it for me, which already has the diagram type (`nodes`, `edges`, `broken`, `caption`) and `layoutDiagram`, a deterministic layered left to right layout.
1. Build the graph without a model where possible: pages or routes, API handlers, schema files, `package.json` services, env names without values. The model only names groups in plain words. Store in project memory with its source, visible and forgettable (rule 15).
2. Reuse `layoutDiagram` so the same project always looks the same.
3. After a change, changed nodes pulse once and the Feature 1 replay walks the path.
4. Click a node to ask about it, routed to Explain.
5. 3D only if users ask.

### Feature 3: a 60 second Squibby explainer, rendered from code

**Why:** one clear video sells a product; a short film of the real product beats a talking head for YC and the site. (Opinion, not a sourced fact.)

**How to build it:**
1. Six scenes of about 10 s: the problem (an agent changed many files, you do not know what), Squibby in the notch, the plain words review, the replay, proof, one tap Undo.
2. Real captures on fixture projects only (`test-shop` style, never a user's project), assembled with Remotion. Remotion is source available, **not MIT**: free for individuals and for profit companies with up to 3 employees; a company licence past that. The licence file also says it "will slightly change" in Remotion 5.0, so re check before relying on it. https://github.com/remotion-dev/remotion/blob/main/LICENSE.md
3. Company licence prices (now confirmed on Remotion's own page): "Remotion for Creators" $25 a month per seat; "Remotion for Automators" $0.01 per render with a $100 a month minimum; Enterprise from $500 a month. The first draft's "$25 per seat or $100 a month" were two different products, not a conflict. https://www.remotion.dev/license
4. Replay scenes can be rendered from Feature 1's drawing programs so the video never drifts from the product. Note: rendering the product's own replays inside Squibby for users would be "building video creation tools", which may fall under the Automators licence; check before shipping that.
5. Keep the calm look: black base, one blue accent, meaning colours only.

## 5. Questions a YC partner will ask (added in the fact check)

1. **"HeyClicky is in YC, lives in the notch, runs agents and draws. Why are you not a feature of it?"** HeyClicky's pages and v1.1.1 notes never mention code review, proof, undo or coding agents (only Xcode as a supported app). Squibby's answer is the trust layer for coding agents. It also needs a plan for when HeyClicky adds "review my agent's changes".
2. **"Does an animated replay make people trust or understand a change better than plain text?"** No evidence yet. Run a small test: same change, text review vs replay, ask users what changed and whether they would ship it.
3. **"What does each replay cost, and who pays?"** Users bring their own key, so every replay spends their tokens. Measure tokens per replay in the spike and show it; make replay off by default if it is costly.
4. **"Is the 3D a gimmick for your users?"** For code there is no physical object; the map (Feature 2) is the useful picture. Keep 3D out of v1.
5. **"Can HeyClicky or OpenClicky copy this in a week?"** The drawing is copyable. The defensible part is the fact sheet: snapshots, exit codes, browser proof, and hooks into seven agent tools.
6. **"Licences?"** three.js MIT, OpenClicky MIT (attribute if adapted), Clicky MIT, Remotion source available with a size limit.
