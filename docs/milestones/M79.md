## 1. Risky packages (T18)

- `runner/src/review/packages.ts` (pure, tested first): from the two snapshots of a review batch, the packages a change added or moved to a new version, read from `package.json` (exact versions, or the version the lock file resolved), `package-lock.json` and `npm-shrinkwrap.json`, `requirements.txt` (`name==version` only), `pyproject.toml` (exact pins), `poetry.lock`, `uv.lock`, `go.mod`, `Cargo.toml` (resolved by `Cargo.lock`) and `Cargo.lock`. A range with no lock file to resolve it is not checked, and said so.
- `runner/src/review/osv.ts` (tested first, with a stand in network): one POST to `https://api.osv.dev/v1/querybatch` with only `{ package: { name, ecosystem }, version }` items, then `GET /v1/vulns/{id}` for each id it names (at most 20 a review). Severity from the record's own rating (`database_specific.severity`, or `ecosystem_specific`) or its CVSS 3 vector's base score. Critical is Must fix (`package_critical`), high is Should fix (`package_high`); moderate and low say nothing. The fixed version is the lowest `fixed` above the version in use. Answers are cached in Squibby's data folder for a day. No answer, a timeout or anything that is not OSV's JSON means "not checked", said in the review's notes, never "safe".
- The finding, in the fixed shape: "<name> <version>: This package has a known serious problem: <id>, fixed in <version>."
- Setting `packages.check` (On, watch, runner). Off: nothing is looked up.
- Docs: `docs/decisions/T18-risky-packages-on-osv.md`, a row in product research section 10 and in `docs/alpha/PRIVACY.md`.

## 2. The weekly summary

- A "This week" row in History opens it, on the press only. Never pushed, never a notification.
- `TaskLog.week(project)` (tested first) counts real rows of the last seven days: changes reviewed (reviews and files), what was caught (keys, weakened checks, false dones, risky packages, the M77 counts), fixes proven, Undos used, copies saved before destructive commands. With it, the decisions and house rules Claude Code is told (memory), and how many reviews found a change against a house rule.
- Protocol: command `week.show { project }`, event `week.summary`. Fixtures read by the runner, the shell and the pages. Never gated.
- `app/src/weekSummary.ts` (pure, tested first) and `weekSummary.tsx`: a plain page; an empty week says so plainly; parts at zero are left out; no streak, no praise.

## 3. Payments, built and switched off

- What exists (T17, M47): Pro by a Dodo license key, checkout in the person's browser, the trial, the gate (`runner/src/plan.ts`), all behind `paymentsOn` in `billing.*.json`. This milestone reuses it, and adds no new flow.
- Prices move out of `strings.ts` into one config, `app/src/prices.json`: Pro $15 a month (the founder, 6 Nov 2026), no yearly price until the founder sets one (so no yearly choice shows), and the one time report at $29. A test fails on a dollar amount anywhere else in the app's code.
- What Free, Pro and the report include is one list in `strings.ts` (`S.m79.includes`), with every limit written as "with limits" until measured.
- The one time report: a third Dodo product (`products.report`), with its own static checkout link and its own key, activated like Pro's but kept apart (it never turns on Pro). Pro includes the report (open question for the founder).
- The remote switch (the payments spec, section 14): `remoteSwitchUrl` in the billing file, empty today. Payments are on only when the file's switch is on, the file can sell, and the remote answer says `{"payments": true}` in so many words. Anything else is off. With an empty address, nothing is asked anywhere.
- Undo and Stop work at every limit (a test reads the gate's lists).
