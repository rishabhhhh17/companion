# T07. Proof: exit codes first, eyes last

- **Status:** Accepted from research; open items checked in M3. Updated 7 Oct 2026 after review.
- **Date:** 2026-10-06
- **Source:** technical_research.md section 1, row 7; section 7 (also section 18 M3 and M4, section 19 pitfalls 21 to 23); product_research.md sections 6, 15, 17 and 19
- **Related:** T05, T06, T08, T10

## Decision
"Done" means proven. After each turn that changed files, the runner climbs a proof ladder: exit code gates, then the dev server from `.claude/launch.json` with `autoPort`, then a Playwright smoke check, then a vision judgment shown only as evidence, then a second model review of the diff.

## Why
- It mirrors Claude Code Desktop's auto verify, which starts dev servers, screenshots, inspects the DOM and fixes what it finds (section 7).
- A vision judge can approve a page with dead buttons. Exit codes and a Playwright click through decide (pitfall 21).
- Agents edit or skip tests to pass. Diffing test files and counts against the checkpoint catches it (pitfall 22).
- False "done" is a high impact risk (product_research.md section 19).

## Alternatives considered
- A vision judge as pass or fail: rejected; screenshots are evidence only (section 1, row 7).

## Added 16 Oct 2026: the ladder on earlier versions (M11)
Which task broke it (T06) runs the same ladder, with its own time limits and no installs, on private copies of earlier saved versions, at most 6 times in one search. A version is judged against the step that fails now: that step failing is "bad", passing or not there yet is "good", and failing earlier says nothing.
Since the Python checks joined the ladder (same day), a Python project (one without a package.json) was not traced back: a private copy had no virtual environment, and only package.json files and lockfiles were compared between versions, so an earlier version could pass or fail only because of its packages. The search said so and checked nothing. Tracing Python projects back needed the venv in the copy, the requirement files in the comparison, and a check that could not run because a package is missing read as unclear, not as a pass. All three were built on 18 Oct 2026 (below).

## Founder decision (7 Oct 2026, F14)
Every user, Free or Plus, gets rungs 1 to 5, including the real browser check, so "done" means the same thing on every plan. Plus adds rungs 6 and 7 (screenshot evidence and the second model review). The pricing table in product_research.md section 15 now says so.

## What this means for the build
Pass signals and timeouts per rung are in technical_research.md section 7.
- Rung 1: install if the lockfile changed, with the lockfile's manager.
- Rung 2: build, typecheck and lint exit 0 per script present (`CI=1`, 5 minute timeout).
- Rung 3: tests exit 0 and the count is not lower than at the checkpoint. Fail if the step edited, deleted or skipped tests (`.skip`, `.only`).
- Rung 4: the dev server answers within 60 s. Never attach to a server started before the step (pitfall 23).
- Rung 5: Playwright smoke: the page loads, no console errors, no failed requests, expected text present, one click through of the changed flow.
- Rung 6: a vision verdict with a screenshot, on the receipt only, never the pass signal.
- Rung 7: a separate read only review session (Opus 5.5 by default) reads the request and the diff, not the author's transcript, and can approve, comment or send back.
- On failure, send the evidence back into the same session, up to two retries within budget, then stop with "not done". The character goes to `error`, never `done`.
- Use Playwright's bundled Chromium, downloaded on first proof, never the user's real Chrome. Proof screenshots show the app under build, never the user's screen.
- M3 builds rungs 1 to 5, the retry loop, receipts and the timeline; rung 7 lands in M4. Rung 6 has no milestone in technical doc section 18 yet; the M3 plan assigns it. M3 passes when five seeded broken projects (Vite, Next.js, static HTML, Express API, Supabase app) never reach `done` while a rung fails, a deleted test is flagged, and the receipt diff matches the snapshot diff exactly.

## What the build settled (hardening pass, 9 Oct 2026)
- Proof commands run with a short allow-list environment (no keys), `CI=1` only for install and tests, and a stop signal that ends everything they started.
- A start command that exits cleanly is a tool, not a website: the start and browser rungs are skipped, not failed. (Since 20 Oct 2026, audit A24: only for a project that does not look like a website. One started from `.claude/launch.json`, a dev script or a Python server, with an `index.html`, or listing a web framework or server, gets a gap instead, so the result is at best passed with gaps.)
- The browser check answers any write request with "no content" while it presses buttons, so a button can never change a server, and a hard deadline always closes the browser.
- The test guard also catches `|| true`, `; exit 0`, `--passWithNoTests`, commented out tests, and counts Python and Go tests. A moved test file is fine when no test is lost.
- A second model answer of "approve, but with concerns" counts as changes needed.

## What the build settled (the browser download, 16 Oct 2026)
- "Downloaded on first proof" is done as a visible, one time download the person starts. Until the browser is there, rung 5 is skipped, the result is "passed with gaps" (never "passed"), and the skipped step carries `needs: "browser"` (so do Point at the problem's answer and a Put it online preview that could not be opened), which is the only signal the card uses to offer "Get the browser check (about 200 MB, once)". Why a press and not on its own: a 200 MB download is never a surprise (AGENTS.md bar rules 7 and 12).
- The press runs Playwright's own installer into `~/Library/Application Support/Companion/browsers` (removed by Delete everything). One download at a time; a second press does nothing; Stop everything and closing the app end it. Only a download with Playwright's finished marker counts as installed, so a download stopped while it unpacked is never used.
- Integrity is Playwright's own: https from Playwright's servers, retried, and thrown away if fewer bytes arrive than announced. There is no checksum of the archive. The person's environment cannot change the download host (the installer gets the short allow-list environment).
- Measured: Chrome Headless Shell 156 (Playwright 1.64, build 1248) is 203 MB on disk on an Apple silicon Mac. Its archive (`chromium-headless-shell-mac26-arm64-1248.zip`) is 103,778,487 bytes, about 104 MB. This was read from a real download that a test started by mistake on 16 Oct 2026, into a temporary folder, before its stand in installer was wired up; those tests now also point the installer at a dead local proxy so that cannot happen again.
- Playwright's installer always adds FFmpeg (a video tool, about 1 MB, from the same servers) to a browser install; there is no option to leave it out. Companion never uses it. It downloads after the browser, with its own progress lines, so only the browser's lines count as progress (the bar never goes back and the size stays the browser's) and FFmpeg is part of "Setting it up". If FFmpeg fails, or the person stops it, after the browser is in place, the card says Ready, because the browser check works.
- The installer runs in its own process group, which the app's force stop of the engine (a stuck engine after Stop everything, a crash, quitting) does not reach. It ends with the engine instead: a helper in the installer's group waits on a pipe that only the engine holds open, and when the engine ends, however it ends, the helper ends the whole group (tested by killing the engine with SIGKILL during a download). This replaces the reviewer's idea of a saved process number killed on the next start: it acts at once, not at the next start, and can never hit an unrelated program that reused the number. Proof rung commands (tests, builds, dev servers) still run without this, so a force stop of the engine can leave one running until it ends by itself; that was not changed here.
- The installer keeps its archive in `browsers/.download`, not the Mac's shared temporary folder, and that folder is cleared before and after every run. A stopped download used to leave its archive (about 104 MB) in the shared temporary folder, because Playwright cannot clean up when it is stopped.

## What the build settled (single tasks and Try again, 16 Oct 2026)
- The fix loop breaker also covers a single task, not only a Drive step. When one task's last three checks fail the same way (same rung, same words once numbers are ignored), the task stops and shows the same card (Try a different approach, Stop here) instead of ending as Not done. A different approach runs inside the same task (one undo point, one receipt) with up to three more tries, and it is offered once per task. Stop and Stop everything answer the card. A Drive plan still asks once per step, after the step's task ends.
- Try again re-runs the last request as a new checked task, giving Claude the failing check redacted and cut to 1,500 characters. It tells Claude how the last attempt really ended: a failed check, or stopped before it finished (the spending limit, an error, or Stop). After a Drive plan it names the last step's title, never the step's instructions, and gets the plan's whole budget, not what the last step had left.
- The tries on a task's check keep counting through a different approach, so a fix after it shows "Fixed after 4 tries", never a plain first pass, and a task that keeps failing says how many checks it really ran.
- After Undo in a project, a follow up or Try again on a task there is refused (the conversation no longer matches the files), and the card hides the box.
- Not yet proven with real Claude: how often a different approach rescues a real task (M11 plan, step 7).

## What the build settled (Python projects, 16 Oct 2026)
- A folder without a package.json that has requirements, a pyproject.toml, setup.py, a Pipfile, manage.py or top level Python files is read as a Python project (`runner/src/proof/python.ts`). A folder with a package.json stays a Node project exactly as before.
- Which Python: the project's own `.venv/bin/python`, then `venv/bin/python`, else a `python3` on the tool path. macOS's `/usr/bin/python3` is only used when Apple's command line tools are there, because without them it opens an install window instead of running. A virtual environment whose Python is gone is called broken, with the commands to make it again; the Mac's Python is not used behind its back.
- Rung 1 never installs Python packages, inside a virtual environment or outside one. It is skipped with a plain note that names the Python used.
- Rung 2: ruff (`-m ruff check --no-cache .`) when the project uses it, else flake8 (with the virtual environment excluded), and mypy (`-m mypy --cache-dir /dev/null`, mypy's own way to keep its `.mypy_cache` out of the project) when configured. Rung 3: pytest (`-m pytest -q --tb=short -p no:cacheprovider`) when there are tests or the project lists pytest. Exit codes decide; pytest's exit code 5 (no tests collected) is "skipped", not "failed". (Since 20 Oct 2026, audit A25: when the test files still have tests, it is also a gap, so the result is at best passed with gaps, never proven.) Every Python command runs with `PYTHONDONTWRITEBYTECODE=1`, so with the flags above no `__pycache__` or cache folder is written into the project. (The first version let mypy write `.mypy_cache`, which the shadow snapshots do not skip; fixed the same day.)
- A check that fails only because a package is not installed (`No module named pytest`, or a `ModuleNotFoundError` for a package the project lists) is a gap: the rung is skipped with the command the person can run (inside a virtual environment), and the verdict is at best "passed with gaps", never "passed". A module the project does not list is a real mistake in the code and stays a failure. The ladder also returns these words (`gaps`, the project's own packages before a lone tool).
- Point at the problem (which never installs) does not call such a project "nothing to check" (fixed 16 Oct 2026 after review; the first version did, which was false for a project with tests and a page). When nothing could be checked because packages are missing, or there is no Python to use (none on this Mac, or a broken virtual environment), the install rung fails with those words and the command to run, the way a Node project with missing packages already did. No place goes with it, so the screen is not looked at for Companion's own sentence. When some checks ran, the verdict stays "passed with gaps" and the card's note line gives the first thing to install. Rescue, which may install, still gets "nothing to check" with the words in each step.
- Rungs 4 and 5: the framework's own dev server (Django `manage.py runserver --noreload`, Streamlit with `--server.headless true --browser.gatherUsageStats false`, uvicorn for FastAPI, `flask run --no-reload`), told `127.0.0.1` and a free port on the command line, with the same start, wait and stop handling as Node. The app's own `python main.py` is not used, because it picks its own host and port. A real FastAPI app through real uvicorn was started, answered and stopped on this Mac in a test (Python 3.9.6).
- Django's runserver opens the default SQLite database on its way up (its migration check only reads), and SQLite makes an empty `db.sqlite3` when there is none (checked on this Mac with Python's own sqlite3: a read leaves a 0 byte file; Django itself is not installed here, so this is reasoned from its code). So after any Python server rung, once the server has stopped, a database file at the top of the project (`.sqlite3`, `.sqlite`, `.db`) that was not there before and is still empty is removed. One that was there before, even empty, or one with anything in it, is never touched. A start that writes tables into a new database (some Flask apps do on import) leaves that file; that is the app's own code, and it is not said on the card yet.
- The visual receipt's earlier version borrows the virtual environment by one link, and a package that is not installed there is "not pictured", never "the page crashed".
- Point at the problem reads pytest's report (long, short, line and summary only), ruff (old and new formats), flake8 and mypy. The pytest, ruff, flake8 and mypy samples in the tests were written by hand in those tools' formats; pytest is not installed on this Mac and nothing was downloaded to capture them, so a real pytest run is still to be checked.

## What the build settled (Python projects traced back, 18 Oct 2026)
- Which task broke it now traces Python projects back. Each private copy borrows the project's own virtual environment (`.venv` or `venv`) by one link, as the visual receipt's earlier version does (`proof/before.borrowVenv`). The checks never write into it (`PYTHONDONTWRITEBYTECODE=1`, pytest with `-p no:cacheprovider`, ruff with `--no-cache`, mypy with `--cache-dir /dev/null`), nothing is installed, and deleting the copy removes only the link.
- The files that decide a Python project's packages are compared between versions like a package.json (`bisect.packagesKey`): requirement files (`requirements*.txt`, `*-requirements.txt`, `constraints*.txt`, `requirements/*.txt`, and the same names ending in `.in`, pip-tools' inputs), `Pipfile`, `Pipfile.lock`, `poetry.lock`, `uv.lock`, `pdm.lock` and `setup.py` whole; `pyproject.toml` and `setup.cfg` without the settings of tools that only check or format code (ruff, black, isort, mypy, pytest, coverage, flake8 and similar) and without the project's name, version, description and links. Everything else counts, a section Companion does not know included, and a file it cannot follow to its end is compared whole. A version whose packages differ is stepped round without a check, as for Node.
- A step that is there but could not run says nothing about that version: pytest finding no tests, a test or server whose package is missing, a page that was never opened. The ladder names these steps (`unclear`, each with whether a missing package was why), and the search reads them as "skip", never as a pass, so the search never moves past the version that broke it onto an innocent task. A step that is not there at all in a version (no tests yet) still counts as not failing, as before.
- The checks step is several checks tried in order (a lint, a type check, a build), so the ladder also names each check it tried and how it ended (`checks`: passed, failed, or could not run because its package is missing). The search reads an earlier version by the check that fails now, by name: failed is bad, could not run is skip, passed is good whatever other check could not run there, and not tried is skip when another check failed first and good when that check was not set up yet. Found in review: with mypy set up but not installed (missing in every version, since every copy borrows the same virtual environment), a step wide "could not tell" made every earlier version a skip, so a ruff failure could never be traced to its task. An unclear answer gives the reason of the step and check that fails now only, never one from another step.
- A project whose own code is installed from a folder other than its top one, where the Python that checks the copies looks, is not traced back, and it says so (nothing is copied or checked): an editable install from `src` or from a build link tree (read from the `.pth`, `.egg-link` and setuptools editable finder files), or a package of `src` installed without `-e`. Every copy would run that installed code, not its own. That Python (the virtual environment's, or with none this Mac's python3, the same one the copies run) is asked once where it imports code from (`proof/python.pythonPaths`: its `sys.path` and standard library folders, asked from an empty folder of Companion's own, writing no bytecode), and every folder it names is looked at, outside the project too: its own site folder and the person's user site (python.org's Python, Apple's with `--user`, pyenv, conda), and the base Python's packages a virtual environment can see. Found in review: reading only the project's `.venv` missed a project with no virtual environment whose src was installed into the Mac's Python, and blamed the task that added the test. A Python that gives no whole answer is not used either. What is inside the project's own virtual environment is borrowed as it is, so its own folders (pywin32's, an old egg) never stop the search, and a src module that shares a name with the standard library is left alone. A flat project installed either way is checked as usual, because `python -m pytest` puts the copy's own top folder first on Python's path.
- Tested with stand ins (stubbed commands, a stand in virtual environment whose Python is a shell script, Python fixture projects) and with this Mac's real Python 3.9.6, which has no pytest: it answers where it imports code from, then the check of now says what to install and no task is blamed. A real pytest run inside the copies is still to be checked on a Mac that has pytest (the test for it skips when pytest is missing).

## What the build settled (checks on a busy Mac, 18 Oct 2026)
- A saved file that git fails to read is read once more, and if that fails too the check stops with that reason (T06). Before, the failed read was taken as the file's text, so one bad read could make Point at the problem say "packages are not installed" in a project that needs none, or let the test guard miss a deleted test file. Shown with a stand in git that fails on purpose; whether this is why the fix eval's row level security case failed once under load is not proven (that failure was not seen again in any run under load).
- A command the Mac had no room to start is run again, and is never read as the project's check failing (`ladder.couldNotStart`, `NO_ROOM`). A very busy Mac can run out of process slots: npm then says `spawn sh EAGAIN` and the shell `fork: Resource temporarily unavailable`, before any of the project's code runs. With the process limit set just above what was running, a right fix of the fix eval's open notes table ended "lint failed. npm error code EAGAIN", the same "failed" its row level security case once gave under heavy load; the ladder read the Mac's problem as the project's. Now the command is run again after 1 and then 3 more seconds; one that still cannot start fails in Companion's words ("This Mac could not start the check because too many programs are running. Close some programs, then try again."), with nothing on screen to point at, and the result says so (`noRoom`), so which task broke it reads that version as unclear and does not trace a check of now that could not start. A test whose own output mentions EAGAIN (a socket read) names no spawn or fork, so it stays the project's own failure and is run once. The eval harness's own checks are run again the same way. This is a cause shown to give exactly that symptom; that it was the cause that one time cannot be shown after the fact. Not covered yet: the dev server's start, and the saved version made before a check (git), which under the same limit sometimes failed to start too and then said Companion could not check the project, never a wrong answer. Each failed final check in the fix eval now records its step (rung, label and words, `finalStep`), and the row level security tests name it when they fail.
- Point at the problem reads at most the last 64 KB of a check's output (every caller already passes only the end of it, 16 KB at most, or a 6,000 character selection), and a file path in it is at most 400 characters. Found when the runner's fuzz test was fixed to really read large output (it had been removing its project folder before the tests ran, so the locator gave up at once): a long run of text with no line break cost time with the square of its length, up to five seconds.
- The failing output a step reports no longer carries stack lines from inside the runtime (`node:internal/...`, `native:`, older Node's `internal/...`). On a busy Mac, Node's test runner prints extra such lines for the same failure (its timers run late), which pushed the last lines of the output down, so the same failure read differently three times and the fix loop breaker never showed its card. Lines that name the person's code or a package are kept.

## What the build settled (audit fixes, 20 Oct 2026)
Found by the audit of 20 Oct 2026 and checked against the code; each is fixed, with tests that failed first.
- **Stop is never a failed check.** A command Stop ended (`aborted`) used to read as its exit code, so the ladder said "The tests did not pass. It stopped with exit code null.", the task stored that as this version's result, and Put it online then refused the version with "The last check of this version failed" and never checked it again. Every rung now ends the ladder as cancelled when the stop signal is set (install, checks, tests, the server, the browser, and the second model's review), the task and the ship check tell it as cancelled, and a cancelled check is never kept as a version's result.
- **Stop reaches the hidden browser.** The ladder and the preview check now hand the browser the stop signal, so it closes at once instead of running until its own time limit (up to 490 seconds with the longest time allowed).
- **A check never runs a script that changes data.** The scripts a check runs by itself (the install's own steps, type check, lint, build, the tests, the dev or start script and `.claude/launch.json`), with the scripts npm runs around them and every script they run by name, are read first (`detect.ts changesData`). One that changes a database (a migration, a push, a reset, a seed), puts something online, publishes, uploads, changes git or reaches another machine is not run: it is a gap, so the result is at best passed with gaps. Before, only a start script chosen in Settings was read, so `"build": "prisma migrate deploy && next build"` migrated the database after every task, on Point at the problem and on every ship check, with no tap (rule 13). Narrower than the start script screen on purpose: clearing build output (`rm -rf dist`) stays in the project, and the hosting tools' local servers (`vercel dev`, `netlify dev`, `wrangler dev`, `firebase emulators`) stay on this Mac. The earlier version for the visual receipt is not started either then.
- **What the task changed in what the project runs asks first.** The checks run outside the sandbox Claude's own commands get, so a task that changed the project's scripts, its packages or their lock file now gets the usual approval card before the check runs any of them ("This task changed the project's scripts or packages. Run its install, build, tests and server to check the work?"). A yes also covers installing the packages, so there is one card. Without a yes nothing of the project's runs and the work is not called checked. Point at the problem, Your turn, a copy of an earlier version and a ship check change nothing, so they do not ask. Still not covered: source and test files a task changed run in the tests outside the sandbox as before. [verify] Running the checks under the same sandbox as Claude's own commands (a profile with the same network list and the same blocked reads) would cover that and make this card unneeded; it needs a real Mac spike first.
- **The check's own guard is not the project's fault.** While pressing buttons the guard answers every write for the server and stops every request to another host. A page that then logged an error or crashed (a Like button reading the JSON answer, a Refresh button loading from Supabase) failed the check, the ring went on the working button and the fix loop spent money on it. Writes are now answered with an empty JSON object (`{}`, status 200), and an error or crash that follows a press the guard answered for is a gap ("Pressing "Refresh" talks to a server, which a check never does, so what it does after that was not checked"), never a problem. A button broken on its own still fails.
- **A website whose start command finishes is not proven** (the line under Decision above), and **pytest collecting nothing while the test files have tests** is a gap (the Python rungs above).
- **A port held by another program is not the project's fault.** A server that hard codes its port (`app.listen(3000)`) stops with `EADDRINUSE` when the person's own copy is already running on it, which is common while building. That read as "The server stopped on its own", failed the start rung, put the ring on the listen line and sent a fix round to Claude. The server's own words for a port in use (Node, Bun, Vite, Next) are now recognised (`server.ts` `busyPort`): the start and browser rungs are skipped with a gap ("Port 3000 is in use by another program, perhaps your own copy of the site, so the page was not checked"), and the earlier version for the visual receipt is not pictured rather than called crashed.
- **More ways of switching a Python test off.** The test guard now also counts `@pytest.mark.xfail`, a `pytest.skip(...)` or `pytest.xfail(...)` call inside a test, `pytest.importorskip(...)` and `@unittest.expectedFailure` as switching a test off, since the `def test_` line stays. Not covered: tests left out through configuration (pytest's `addopts`, `-k` or `--deselect`, `collect_ignore`, a vitest or jest exclude) and reading pytest's summary line for new xfailed, skipped or deselected tests.
