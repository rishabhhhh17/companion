# T16. One settings registry, read by the shell, the pages and the engine

- **Status:** Accepted (M11, customize core). Built and tested with fakes; not yet tried in the built app by a person (see "Not proven").
- **Date:** 2026-10-19
- **Source:** the founder's "customizable everything" direction (every behaviour gets a Settings control with a safe default); `docs/milestones/M11-customize-plan.md`
- **Related:** F17, F18, T05, T13, T14

## Decision
Every setting a person can change is described once, as data, in `protocol/settings.json`: its name, section, kind (switch, choice, number, text, list, or custom for the editors that already existed), its usual value (today's behaviour), its limits, whether it is per project, who applies it (shell, engine, pages), where its value is kept, and whether it takes effect at once or from the next task. The shell reads the file with `include_str!` (`app/src-tauri/src/settings.rs`); the pages and the engine read it through `protocol/settings.ts`. The words a person reads are in `app/src/strings.ts` (`S.set`, `S.sections`), never in the registry (rule 21).

The rules for what a value may be are written twice, in Rust and in TypeScript, and both run every case in `protocol/fixtures/settings-cases.jsonl` (valid, refused and tidied cases for every kind, and the migration cases), so they agree on each of them. The check that text "looks like a key or password" is the shell's own `redact::is_sensitive`, written again in `settings.ts`.

## Where values are kept (the stored file this record adds)
A new file, owned only by the shell: `~/Library/Application Support/dev.companion.app/settings.json`, owner only (0600), written whole and atomically under one lock:

```
{ "version": 1, "values": { "<name>": <value> }, "projects": { "p_<12 hex of sha256 of the folder path>": { "<name>": <value> } }, "migrated": ["pageStorage.v1"] }
```

- Only values that differ from the usual one are written, so putting a setting back means removing it.
- Names and fields this version does not know are kept untouched, so going back a version loses nothing. A value of a setting this version knows but refuses (a newer version's new choice or wider range) is kept too: not in force here (the usual value is, and the bad value is listed), written back exactly as it was on every save, in the app's values and in each project's, until that setting is set or reset in this version (`settings.rs` `held`, found in the audit of 20 Oct 2026).
- A project's values are kept under a hash of its folder, never under the path.
- A file that is not JSON (or not text) is moved aside as `settings.damaged.json` (kept for support) and Companion starts on the usual values, with one plain line in Settings. The migration mark is kept, and a fresh file holding only it is written at once: a settings.json is only written after Home has run the migration, so the damaged one had it, and without it the old page storage would copy the choices from before the update back in. One bad value falls back to its usual value and is listed.
- A file that is there but cannot be read at all (no permission, an I/O error, a folder in its place) is not damaged: it is left where it is, Companion uses the usual values for that session with one plain line in Settings, and nothing is saved over it. Each change that would write settings.json first reads it again; while it still cannot be read the change is refused ("Could not save that setting. It is unchanged."), and once it can, its values are taken first. A reset that finds it readable again resets nothing: the page was shown the usual values, not the person's own, so it could neither name them first nor put them back with Undo. Every window is told what is in force now and the page says so in one line (`readAgain`), so the person can look and reset again.
- Both files are in Companion's own folder, so Delete everything already removes them (a `wipe.rs` test proves it); `dev.json` still stays.

Wrapped, left where they always were (moving them would be risk for no gain): `dock.json` (Come to what it is about, and since area 4 the character's place on the display it is on: its edge, its position along it, and Same place on every display), `presentation.json` (hide from screen sharing, quiet during calls), `keys.json` (its own editor and checks), `voice.json` (its own editor), and from area 2 each project's own `.companion/rules.txt` (house rules, store `rules`, `houserules.rs`): the file stays the source, read for the row and written only when the person presses Save, keeping every line it does not understand exactly, never through a link. The engine reads that file itself before every action, so it is not in `settings.apply`. Since M11 area 5, `prompt_help.json` is wrapped too (the per app answers for Prompt help and the error explainer, `ph.appAnswers`, store `promptHelpApps`: its own editor, the third and last custom row; it is the only protective custom setting, so no reset ever touches it, and its rules stay in `prompthelp.rs` `Consent::change`: the built in never list cannot change, an app the person said never to read is loosened only after an inline confirm, and "Ask each time" is now kept as `"ask"`, which a version before reads as no answer, the same meaning). The engine keeps its own three, reached only through its own commands, which only the shell sends now: `spending.json` (the daily limit, `spending.set`), `memory-settings.json` (Explain after a task and pausing, `explain.set` and `memory.pause`; since M11 area 3 Explain is a choice, `explain.mode`, written as `explainMode` with the old on or off switch beside it, and an older file keeps its meaning: off is off, on is reasons and a question), `metrics.json` (beta numbers, `metrics.set`). The money path (the daily limit, `COMPANION_DAILY_CEILING_USD`, the real run daily limit scenario) is unchanged. These apply to every project, so with no folder chosen the shell names the stand in project, and the engine reads and writes no folder for it (profile only memory, nothing spent).

## How a change travels
Pages never write a file. Every change goes through the shell (`settings_set`, `settings_reset`, `settings_migrate`, Home's window only; `settings_get` from any window). The shell checks it, keeps it, applies its own part (for example sends a visiting character home, applies the screen sharing setting, silences speech), then tells every window (`settings-changed`). What the engine applies from `settings.json` reaches it as the protocol command `settings.apply` (values that differ from usual, and the current project's own). It is the first line the engine reads after every start and restart (queued on the new engine's own queue before anything else can reach it, `runner::supervise_first`), and it is sent again after each change the engine applies and when the project folder changes, to another folder or to none (the open practice copy removed), through one place (`main.rs` `project_now`). It is not on the page allow list, and neither are `spending.set`, `explain.set`, `memory.pause` and `metrics.set` any more. The engine checks every value again, keeps them in memory only, answers `settings.applied` (names only), and a task reads what it needs when it starts, so a running task keeps the values it started with.

## Migration
The choices the pages kept in their own storage before the registry (reactions, Your turn, text size, Speak to me, Answer out loud, auto send, Show me on all screens, the daily update check) are read once by Home's window with exactly today's meaning and sent to `settings_migrate`. The shell keeps only ones not already set and only valid ones, records `pageStorage.v1` and refuses a second run. Until the mark is in the snapshot, every window reads the old page storage for these, so nothing shows a choice the person did not make. Storage that cannot be read migrates nothing and is tried again next time. The old page storage is not deleted for one version (going back still works); Delete everything removes it with the rest of the page storage, as before.

Once the mark is in a snapshot, page storage also keeps one value of its own, `companion.settingsMigrated` = "1" (the only thing the pages write there for settings). With it, the old page storage is never read again and the migration sends nothing (it only records the mark again), so a settings.json lost later (damaged, or removed by hand) never brings the choices from before the update back. Delete everything clears page storage and settings.json together.

## Reset
One setting (Reset, only when it differs from usual), a section (Reset this section), or everything (Reset all settings to usual). Both of the last two ask first, naming every setting that will change (so someone who paused learning reads "Pause learning" in the list), and both offer Undo for ten seconds. Protective settings (lists a person adds protections to, such as house rules later) are never in a section or everything, and are never reset from their own row. Reset all covers settings.json (the app's values and this project's; from area 2, another project keeps its own, because the page was shown only this project's and could neither name the others first nor put them back with Undo), the wrapped stores (keys through the same path as Reset to the usual keys, voice to the Mac's own choices) and the engine's three (daily limit $10, Explain after a task back to reasons and a question, learning on, beta numbers off; their counts stay). It never touches the key, project folders, memory lines, history, undo points, pictures or anything protective. What a reset changes is decided by the shell from exactly what the page was shown (`settings.rs` `reset_plan`: each setting in it whose shown value differs from its usual one), and the page keeps the same list for Undo (`settingsStore.ts` `undoValues`); both run `protocol/fixtures/settings-reset-cases.jsonl`, so Undo puts back exactly what was reset. The engine keeps its own three, so the page names the ones it has heard away from usual, and the shell resets only those: one the page has not heard yet is left as it is (the confirm says so), because the page could neither name it nor put it back. Undo puts every value back through `settings_set`, the voice and the keys only exactly as they were shown (`voice_from`, `keys_from`; keys one job at a time through the same switch Change uses). A value shown rounded carries its exact value for Undo in the snapshot's `restore` (since area 4, only the character's position, shown on its 5 percent step: a place dragged off the step is sent back as `{"fraction": ...}`, `place_from`), so Undo puts the character back exactly where it was; the shared reset cases cover it.

## Why
- One list means the Settings page, search, Reset, the migration, the engine and the tests all come from the same place; a new setting is one definition, its words, and the code that reads it.
- JSON, not TypeScript, so the Rust shell reads exactly the same file with no build step.
- The shell is the only writer, so a page (which runs web code) can never write a setting file, and every value is checked where it is kept.
- The engine's own stores stay its own, so the spending limit and memory rules keep their tested code paths.

## Stored data added by area 5 (pointing, talking and other apps)
- `settings.json` may now hold the bundle ids of up to 20 apps the person added to Apps that count as a call (`calls.apps`), with Add the app in front. Only the id of the app in front is read, on that press (rule 7). Only ids can be kept: a list may name an item shape (`item.shape`, today only `appId`: letters, digits, dots, dashes and underscores, up to 200 characters, no leading dot and no two dots in a row), checked by both rule sets and the shared cases, so anything else is refused with "Only an app's id can be kept here". It is in Companion's own folder, so Delete everything removes it.
- `prompt_help.json` may now hold `"ask"` for an app, and Settings' "Add the app in front to never read" writes `"never"` for the app in front (its id only). The page names the app first and sends its id; the shell refuses if another app has come to the front since.

## What this means for the build
- A new setting needs a definition in `protocol/settings.json`, its words in `S.set` (a test fails without them), and its reader. Never a plain setting as `custom`.
- Read a setting in a page with `setting(key)` or `useSetting(key)` (`app/src/settingsStore.ts`); in the engine with `RunnerSettings.get(key, project)`, once, when a task starts; in the shell from `settings.rs`.
- The worked example is `work.maxTurns` ("Most turns in one task", 20 to 200, usual 80), which reaches the SDK's `maxTurns` for tasks, Drive, Rescue, Research and planning.
- Never a setting for anything in `docs/milestones/M11-customize-plan.md` under "Never a setting".
- A choice whose other options come from the project (area 2's start script, `optionsFrom: "projectScripts"`) takes only the plain name of a script that starts the project: dev, develop, start, serve or preview, alone or with more after a `:._-` (dev:web, start.local), up to 60 characters, checked the same way by both sides (`settings.ts` `isStartScript`, `settings.rs` `start_script`, the shared cases). A build, a lint, the tests, an install step or a deploy can never be chosen. The engine is the boundary: at use it checks again that the script is in package.json and that neither its name, its own text, the scripts npm runs around it (pre and post) nor any script they run sound like they put something online, publish, delete, or change data or git (`proof/detect.ts` `usableStartScript`), and the Settings row offers only those. Anything else means the usual way, said as a gap. A chosen script that finishes without opening a page is a gap too, and the project is started the usual way, so the browser check still runs (F14). It is never a box to type a command in.
- A change for one project says which project the page was shown it for (`settings_set`'s `project`; house rules always do). The shell keeps it only while that is still the project in Home (`settings.rs` `for_project`, else "projectChanged"), and writes house rules to the project the list came from. The folder can change by itself (a copy from a link that finishes opens its folder), and one project's rules must never be written over another's.
- House rules are the person's own protections, not a task's work, so no Undo changes them (`checkpoints.ts` `KEPT_ON_UNDO`): putting a version back, undoing that undo, or undoing one task in the middle leaves `.companion/rules.txt` exactly as it is now, there or not. Before area 2's review fix, Undo put back the rules file from before the task, so a rule added in Settings after the task was quietly dropped. The file stays in every snapshot, so a copy of an earlier version (a before picture, which task broke it) still has its rules.
