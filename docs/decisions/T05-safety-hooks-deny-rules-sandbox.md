# T05. Safety: hooks, deny rules and the sandbox

- **Status:** Accepted from research; open items checked in M1 hook tests. Updated 7 Oct 2026 after desk research and review.
- **Date:** 2026-10-06
- **Source:** technical_research.md section 1, row 5; section 8 (also section 1 prototype lesson one, section 3 permission modes, section 19 pitfalls 6, 14, 15, 24 and 28, section 20 questions 6 and 7)
- **Related:** F03, T02, T06, T08, T09, T15

## Decision
Safety lives in `PreToolUse` hooks (code that runs before every tool call and can block it), scoped deny rules and the macOS sandbox. `canUseTool` is only the approval UI for calls that fall through.

## Why
- The SDK checks hooks, deny rules, ask rules, the permission mode and allow rules, and only then calls `canUseTool` (section 1, prototype lesson one).
- The prototype's outside the folder guard lived in `canUseTool`. Under `acceptEdits` the SDK approved `Write` and `Edit` first, so the guard was dead code.
- Deny rules hold "even in `bypassPermissions` mode". Among hooks, `deny` beats `defer` beats `ask` beats `allow`, and a hook `allow` does not skip deny or ask rules (section 8).
- Instructions are not controls: Replit's agent deleted a production database during a code freeze despite instructions (section 6).

## Alternatives considered
- A regex blocklist in `canUseTool` alone (the prototype): bypassed by `acceptEdits`. The regex list survives as one input to the hook.
- `auto` mode: an experiment only. Anthropic can turn it off server side, and it "does not guarantee safety" (pitfall 15).
- `bypassPermissions`: never.

## What this means for the build
The layers are in technical_research.md section 8. Rules a coding agent must never miss:
- Sandbox: `allowUnsandboxedCommands: false`; the network allowlist starts empty (add package registries and the project's declared API hosts). It covers shell commands only. If it cannot start, show `error_during_execution`; never run unsandboxed (pitfall 14).
- Deny rules in `disallowedTools`: `Bash(sudo *)`, `Bash(rm -rf *)`, publishing and deploy commands. Whether `Bash(git push*)` joins them is the open item below; deny beats ask, so a denied command can never reach an approval.
- Deploys run through the runner's Ship adapters (T08), not agent Bash, so the deploy deny rules do not block Ship.
- `PreToolUse` hook: resolve every path and deny writes outside the project; deny `.env*` edits unless the step is about secrets; classify irreversible actions; return `ask` for the approval UI. Agent commands that would change the user's git need approval (section 6).
- `canUseTool` renders approvals; leave `permissionPrompts: 'host'`.
- Pre ship gates: gitleaks on the diff and built client bundles; block shipping when a Supabase table exposed to the Data API lacks RLS (T08).
- Project trust: on first open of a folder, list its hooks and MCP servers and ask before loading them (pitfall 24). A project's `.claude/settings.json` can set `apiKeyHelper`, which outranks a plan login (T03).
- Never give the agent production database credentials; require approval for any command that targets production.
- Native Windows has no sandbox, so more Bash patterns move into ask rules there.
- M1 hook tests: a write to `../outside.txt` is denied under `acceptEdits`; `git push` behaves as the M1 plan settles it; a $0.05 budget ends with `error_max_budget_usd` (section 18).

## What the build settled (hardening pass, 9 Oct 2026)
- The sandbox is on for macOS shell commands, `allowUnsandboxedCommands` is false, and writes are limited to the project, its caches and the package caches. The network allowlist holds the package registries and local servers only.
- The sandbox does not cover the Read tool, so private folders (keys, browser data, mail, Keychains, Companion's own data) also have `Read(...)` deny rules. Both were checked with real Claude.
- `settingSources` is empty, so a project cannot bring its own hooks, environment or `apiKeyHelper`. Its `CLAUDE.md` is passed as plain notes.
- Writes to `.git`, `.claude` and `.companion` are always refused, and shell commands are read through `sh -c`, `env`, `xargs` and similar before judging them.
- Account variables (`ANTHROPIC_*`, cloud and OAuth ones) and injection variables (`NODE_OPTIONS`, `DYLD_*`, `BASH_ENV`) never reach Claude Code or what it starts.
- `ToolSearch` is allowed (research needs it to reach web search).
- Known limit: installs inside the sandbox need Node 20 or newer, because Node 18 cannot reach the sandbox proxy.

## What the build settled (config and safety pass, 16 Oct 2026)
- The `PreToolUse` hook has its own time limit set (`HOOK_TIMEOUT_SECONDS` in `runner/src/sdkEngine.ts`, 32 minutes), longer than an approval card lives (30 minutes, `APPROVAL_TIMEOUT_MS`). An unanswered card ends as a no, and that no reaches the SDK before it could give up on the hook. Not yet seen on a real run: what the SDK does when a hook does time out.
- Background commands, read from the pinned SDK (0.3.293): a background command is stopped with `TaskStop` (`KillShell` and `KillBash` are its old names, mapped to it). `BashOutput` and `TaskOutput` were removed; output is read with `Read` from Claude Code's own file. The binary keeps it at `<CLAUDE_CODE_TMPDIR, or /tmp>/claude-<uid>/<project>/<session>/tasks/<id>.output`. Stopping or reading a command the same task started is allowed; anything else asks, and unknown tools still ask. The task learns the id from the shell result's `backgroundTaskId` in the `PostToolUse` hook. **[verify]** on a real run that the hook carries it; if it does not, these calls ask, as before.
- Reading that output file is allowed only at exactly that place (`claudeTempRoot` in `runner/src/safety.ts`), and only when no part of the way from Claude's temp folder to the file is a link. A review found the first version accepted any folder named `tasks` and followed links, so a link the agent made with a script could read a file outside the project without a card. Known limit, shared by every read the hook allows: a file can be swapped for a link after the check and before Claude reads it. The `Read(...)` deny rules on private folders still apply at read time.
- "Allow for the rest of this task" (`approval.resolve` with `scope: "task"`) remembers that exact action (the tool, the exact file, pattern or input, and the reason Companion asked) for that task and agent only, never across tasks, and is cleared by Stop and Stop everything. It covers only two kinds of question (`taskScopeCovers` in `runner/src/safety.ts`): a file tool reading outside the project, and a file edit or read inside it that only a house rule asks about. Every command asks every time (a script can change between runs, and git, installs and deploys are not safe to repeat), and so does every web fetch, every other tool (some send or publish) and anything that cannot be undone (rule 13). It never overrides a refusal. A Drive plan is one task: the yes holds for every step of that plan, including a retry and a resume after a pause, and ends with the plan. After Stop nothing more runs or is asked in that task. The app does not offer this answer yet; it still sends "once".
- Installs on the Mac (`brew`, `port`, `apt`, `gem`, a global `npm`, `pnpm` or `yarn` install, `pip install` outside a project environment) ask and are now marked not undoable, as technical_research.md section 6 says. They were marked undoable before.

## What the build settled (settings area 1 review, 19 Oct 2026)
- Claude Code's sandbox no longer runs a shell command on its own say so: `autoAllowBashIfSandboxed: false` in `sandboxSettings` (`runner/src/sandbox.ts`), checked by a test on `buildSdkOptions`. Claude Code's default is true, which lets a sandboxed command through its normal permission flow without asking. Companion's hook answers every command itself, so its explicit allow is what runs a command and normal work should not change; but if Claude Code ever gave up waiting on the hook while a card was open, a command in `acceptEdits` would have run inside the sandbox without a yes. With it off, such a command goes on to `canUseTool`, which always says no. Not proven on a real run: that a hook allow still runs a sandboxed command with it off (the real run checklist).
- "How long a question waits for your answer" (`approval.waitMinutes`) goes from 5 to 30 minutes, not to 120 as first planned, so the hook's limit stays at 32 minutes, exactly as before the setting. A longer limit is the open item above. Even with the auto allow off, an edit inside the project that only a house rule asks about would still go through `acceptEdits` if the hook were given up on, so the top rises only after a real run proves the longer limit.

## What the build settled (audit fixes, 20 Oct 2026)
- **Data in a web address, however it is split.** A web fetch asked only for a query string, an address over 300 characters or one path part of 40 code-like characters, so a key spread over short path parts or put in the host name went out with no card. The code-like parts of the host name and the path now count together (40 characters in all asks), and a code-like host label of 20 characters or more asks too.
- **Every way of reading asks outside the project.** tar's and zip's sources, the archive tar, unzip and the decompressors open (gzip, bzip2, xz, zstd and others), dd's `if=`, plutil, `defaults read` of other apps' settings, cpio (which reads the files it is handed), and `<` input redirection for any command now ask when they read outside the project; ditto is a writer like cp. Review fix: tar making an archive from a list (`-T`, `--files-from`) and zip reading names from its input (`-@`) always ask, as cpio does, since the files they read cannot be checked first; the list file itself (`-T` when unpacking, zip's `-i@` and `-x@`) and another archive copied in (tar's `@archive`) are judged like any read; split, iconv and openssl (`-in`) are readers too. The text of a here document (`cat > page.html <<'EOF'` ... `EOF`) is data, so a `</div>` in it is no longer read as `<` from a file, and `<<` inside arithmetic is not taken for one. These are the ways of reading the tests cover (`runner/test/audit-safety.test.ts`, `audit-recheck.test.ts`); a program that opens files its own way is not in them.
- **git pointed at another folder asks.** `-C`, `--git-dir` and `--work-tree` (in both spellings) outside the project, and files outside it named to diff (`--no-index`), blame, show, log and grep, ask as reading outside the project. Review fix: git's own environment variables do the same, so `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY` and the like outside the project ask too, in front of git, after `env`, through `export` or inside `sh -c`; those that make git run a program or read other settings (`GIT_EXTERNAL_DIFF`, `GIT_SSH_COMMAND`, `GIT_PAGER`, `GIT_CONFIG_GLOBAL` and others) ask like `-c`.
- **A version bump is a git change.** `npm version`, `pnpm version`, `yarn version` and `bun pm version` make a commit and a tag in a git project, so they ask (risk git), unless told not to (`--no-git-tag-version`). Review fix: the flags are read in order and the last one wins, as npm reads them, so `--no-git-tag-version --git-tag-version` asks. Not done: also making the project's `.git` a place the sandbox refuses to write, since that would break a git command the person approved on the card (rule 10 lets them).
- **git grep's pager runs a program.** `-O` and `--open-files-in-pager` ask, like `--ext-diff`.
- **House rules see in place tools.** A never edit or ask edit rule now covers formatters and fixers told to write (prettier, eslint, biome, stylelint, black, ruff, isort and others, run directly, from `node_modules/.bin` or through npx, bunx, pnpx, npm exec, pnpm dlx), awk with `-i inplace`, and package managers writing package.json and their lock files (adding or removing packages, `npm pkg set`, a version bump). A formatter pointed at a folder that may hold a protected file asks, since which files it changes is not known in advance.
- **The proof ladder's commands were not in the sandbox** (closed 31 Oct 2026, see "The safety box for checks" below). They ran with the short allow-list environment only (`proof/exec.ts`). A task that changed the project's scripts, packages or lock file asked on the approval card before the check ran them, and a check never runs a script that changes a database or puts something online (T07, audit fixes). Source and test files the task changed still ran in the tests outside the sandbox.

## Revisit if
An SDK upgrade changes the permission order or hook precedence and the M1 hook tests fail. Upgrades happen only on a branch with the full suite (pitfall 28).

## The settings file guard (22 Oct 2026)
- T05 always said the hook denies `.env*` edits unless the step is about settings, but a real task on 22 Oct found the hook allowed every write: an Edit, a Write and a shell redirect all went through with no card (the agent also read the whole file). Now any write to a private settings file (`.env`, `.env.local`, `.env.production`, any `.env.*`, `name.env`; never the shared templates `.env.example`, `.sample`, `.template`, `.dist`, `.defaults`) asks first, whatever the tool: Edit, Write, MultiEdit, and a shell append, `sed -i`, `tee`, `cp`, `mv`, `rm` or `truncate` (`isSettingsFile`, `settingsVerdict` in `runner/src/safety.ts`).
- The card is a new kind, `settings`, and says `changes your private settings file (.env): SITE_NAME`: **names only, never a value**.
- A name that looks like a key, token or password (`SECRET`, `TOKEN`, `PASSW`, `PRIVATE`, `CREDENTIAL`, `AUTH`, `CERT`, `API_KEY`, `ACCESS_KEY`, `KEY`) is refused, with "add that line yourself". Companion never writes a secret (the agent's instructions say the same, so this is the backstop, rule 12).
- A yes for the rest of the task never covers a settings card (`taskScopeCovers`). Undo restores `.env` changes as before (T06's `.env` vault).
- The agent is told it may add a plainly harmless setting (a shop name, a currency, a public address) as one appended line, and that Companion asks first.
- **Reading closed (22 Oct 2026, founder said yes).** No task reads a private settings file any more, in any spelling: the Read, Grep and NotebookRead tools refuse it, and so does any shell command that names one (`cat`, `head`, `grep`, `sed -n`, `awk`, `cut`, `source`, `cp` out of it, `tar`, `zip`, `curl -d @.env`, `git diff .env`, `docker --env-file .env`, and a glob like `.e*`), and `< .env`. Looking for it (`ls`, `stat`, `test -f`, `wc`, `git check-ignore`) and the shared templates (`.env.example`) stay allowed. `grep -r` and `rg --hidden` refuse when the folders they search hold a settings file, unless an `--exclude` names it. A line can still be renamed in place with `sed -i`, which is a tap, without ever reading it. Plan, Rescue and Research already refused reads.
- **The attack of 22 Oct 2026** (131 disguised writes and reads, two rounds, no model spend). Round one found nine writes that got through: `sh -c`, `bash -c` and `eval` hid the redirect inside the quotes (an older gap that also let a write outside the project past the hook, though the macOS sandbox still stopped it), `sed --in-place`, sed's own `w` command, globs such as `rm .e*`, and `split`. Round two found the editors and in place tools (`sponge`, `ex`, `vim -es`, `ed`, `yq -i`, `awk -i inplace`, `patch FILE`), `bun -e`, `node` reading code from a here document, process substitution, and `.envrc`. All are now asked or refused (`runner/test/settings-file-guard.test.ts`, about 150 cases).
- **Known limits, not closed:** a script the project runs (`npm run x`, `make`) can write any file, `.env` included, and nothing here can see inside it; a patch file can name `.env` inside itself; `git diff`, `git log -p` and `git grep` with no path can show a tracked `.env` (a settings file is normally untracked); `unzip` can extract an archive's own `.env` into the project; a hard link made with `cp -l` or `ln` to a settings file is not seen. The macOS sandbox still bounds all of it to the project folder.

## The safety box for checks (security audit, 31 Oct 2026)
- **The gap.** The security audit of 31 Oct 2026 (`proof-unsandboxed-checks-run-agent-edited-code`, high) showed that a check ran the project's own code outside every box: a test, a source file or a config the sandboxed agent wrote ran as the person, with the real home folder and the open internet, with no card, because the scripts card only fingerprints the run files. For a Python project the card was skipped altogether.
- **Now every proof command runs in macOS's own sandbox** (`sandbox-exec`, `runner/src/proof/box.ts`): the install, the build and lint and type checks, the tests, the project's server, the visual receipt's earlier version (its own server, since the review of 31 Oct 2026; where the box cannot be used it is not started and there is no picture), the watch's build and tests, in a task's check, Rescue, Put it online, Point at the problem, Your turn and which task broke it. Its rules come from the same lists as the agent's sandbox (`runner/src/sandbox.ts`): writes only to the project, the package caches the agent may write and a temporary folder of the command's own (its `TMPDIR`, removed afterwards); no reading of `sensitivePaths` (logins, keys, Claude's and Companion's data, the Keychain, browsers, mail) and of Companion's data folder when it is moved (`COMPANION_DATA`), with one exception: a project that is one of Companion's own private copies inside that data folder (which task broke it, the earlier version's picture) is read like any project, while the rest of the data folder stays refused; no writing any app's preferences (`user-preference-write`, which cfprefsd would otherwise write into the real `~/Library/Preferences`); never a write to the project's `.git`, `.claude`, `.companion`, `.vscode`, `.idea`, `.mcp.json` or `.gitmodules` (rule 10). No opening apps or documents (Launch Services), no Apple Events, no launchd jobs, no clipboard, no signals to programs outside the box.
- **Network.** The sandbox sees addresses, not host names, so the registry list cannot be expressed. The build, the checks, the tests and the server reach only this Mac (loopback, and sockets inside the project or the temporary folder; not the name lookup service, which could carry data out in a name). An install, and a native build or server the person allowed to download (the install setting, T07), keep the internet: they are their own approved rung.
- **Every path is a parameter** of the rules (`sandbox-exec -D`), never their text, so no folder name can change them (a test uses a folder named with quotes, parentheses, `$( )` and backticks).
- **Two folders of macOS's own per person folders** are writable because Apple's build tools fail without them: Clang's and Swift's module cache (`getconf DARWIN_USER_CACHE_DIR` + `clang/ModuleCache`) and the folder macOS saves a file through (`DARWIN_USER_TEMP_DIR` + `TemporaryItems`, xcodebuild's logs). SwiftPM cannot put its manifest in a sandbox of its own inside this one (macOS gives a program one sandbox: "sandbox_apply: Operation not permitted"), so in the box `swift build`, `swift test` and `swift run` get `--disable-sandbox` and the box holds the manifest instead (`native.ts swiftInBox`).
- **Without the box** (no `sandbox-exec`, or the rules refused for that project, tried before each check by listing the project from inside the box, so a box that cannot read the project counts as not working): nothing the check would run runs without a yes in that check, whatever changed (an "unboxed" card: "The safety box for checks is not working on this Mac..."), and a check with nobody to ask runs nothing and says so. A command meant for the box never runs outside it (code 126).
- **The scripts card stays.** The box makes the card's reason weaker, not gone: a changed script still runs on this Mac with the project's files, so it still needs a yes. Its words no longer say the commands run outside the safety box. The Python path now goes through the card too (its `.replit` and `.claude/launch.json` starts are the project's).
- **The approval record now starts as a task starts** (`proof-first-check-approves-unchecked-agent-changes`, medium): an empty record is filled from the task's before snapshot, the project before the agent wrote anything, never by whichever check comes first. Every agent that can write runs through that one start (`runInnerBody`); Plan, Research and Rescue's look only. A task that changed `package.json` and ended before its check (an error, a limit, Stop) no longer has its scripts run unasked by Point at the problem, and Put it online asks "changed since you last said yes".
- **Checked on this Mac (31 Oct 2026, macOS 27, `runner/test/proof-sandbox.test.ts` and the suites below):** the rules compile and apply; a write outside the project, into the stand in home folder or into `.git` is refused while a write in the project and in `TMPDIR` works; a read of a dummy key in a stand in `~/.ssh` and of Companion's data is refused; `localhost`, `127.0.0.1` and `::1` work from inside (Bun, Node and curl), the runner reaches a boxed server, and a connect to a documentation address (192.0.2.1) is refused with "Operation not permitted"; the watch's way of running a command is boxed; real `npm run test` (audit-ship A12), real `cargo` build and tests, real `swift build` and real `xcodebuild` builds pass in the box.
- **[verify] on real projects:** a real `npm install`, `pnpm install` and `bun install` with packages that build native code (node-gyp, writing `~/.node-gyp` is refused), postinstall steps and husky (it writes `.git`, refused); Next.js builds that fetch Google Fonts at build time (no internet in the build: since the review of 31 Oct 2026 that is said as a gap, never sent to the fix loop); tests that call real services; Gradle and Maven (not run here); an Xcode project with Swift packages (SwiftPM inside xcodebuild may need its manifest sandbox turned off too); Python with a real virtual environment and pytest plugins; whether a DNS lookup of an internet name is really refused in every tool. Not boxed yet: the Python question in which task broke it (`proof/python.ts pythonPaths`, the project's own Python runs its `.pth` files there) and the install the person presses (`agent.ts`, `npm install` from the Install button).

- **Review of 31 Oct 2026, what the first round left open.** (1) The earlier version's server for the visual receipt ran outside the box; it runs in it now (above). (2) The box refused reading Companion's own data folder, where which task broke it and the earlier version's picture keep their copies, so every check of a copy failed (and the search could blame the wrong task); a copy inside the data folder is now readable as the project (`box.ts`, a test with the shipped folder layout under a stand in home). (3) A refusal by the box itself (a write to a fixed `/tmp` path, a browser that keeps its own sandbox on, a name on the internet that cannot be looked up, Next's font download) is a gap with plain words, never the project's failure and never a fix round (`box.ts boxRefusal`, `ladder.ts`); reading a private place stays a failure. (4) The package managers' own settings files (`.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.pnpmfile.cjs`, `pnpm-workspace.yaml`, `bunfig.toml`) and a Yarn of the project's own or its plugins (`.yarn/releases`, `.yarn/plugins`) are part of the run fingerprint, read from the project folder as it is so one git ignores is not missed; a project without them keeps its fingerprint (`approvedruns.ts`, `livefiles.ts`). Not done on purpose: refusing the project's `.env` to an install (Bun's install reads `.env` and stops with EPERM), and `--ignore-scripts` (packages that build or download in postinstall would break). Still open: the project's own install steps (`prepare`, `postinstall`) can run a file of the project's that a task changed, with the internet, when the packages are missing. (5) Preferences cannot be written from the box. Checked on this Mac: `xcodebuild -version` and a tiny `swift build` give the same result with and without that rule; that `swift build` fails in the box here either way (`xcrun` cannot write its cache in the per person temporary folder, then the link is refused), so the earlier line "real `swift build` ... pass in the box" needs checking again.
- **Review of 31 Oct 2026, the agent's own commands.** `$'...'` quoting is read the way bash and zsh read it (`shell.ts`), so what it would hide is judged, and a line that uses it always asks at least (its escapes can spell a word no reader sees); inside `"..."` a backslash now stays before anything but `$`, `` ` ``, `"`, `\` and a newline, as in the shell. A web address is judged on every piece of its path and names, however short or punctuated, with a limit on free text (120 characters); plain words under that limit still pass, since a page name cannot be told from a sentence. A fetch that asks is looked up in DNS only after a yes, and refused then if it leads home. Claude Code's sandbox is told never to write the project's `.companion` and `.claude` folders (`sandboxSettings` `denyWrite`). **[verify]** on a real run (`real-sandbox.ts`) that a script the agent runs is really refused there; until then the safety hook is what refuses it.

## The audit's leads that need a real Mac (security audit, 31 Oct 2026)
The audit's `NEEDS-VALIDATION.md` lists eleven leads that source alone could not prove. The cheap changes that cannot break the product are made, each with its own tests; what still needs a real Mac stays open below.
- **Lead 1, the engine a release starts.** A release build (no `debug_assertions`) never takes Bun or the runner from `dev.json`, `COMPANION_BUN` or `COMPANION_RUNNER`, and it takes away a `COMPANION_CLAUDE_BIN` it inherited unless the installed build passed its check (`runner.rs locations_for`, `claude_env`, `engine_command`; both profiles tested as plain functions). A development build works as before, so `app/scripts/dev-setup.sh` still works. Still open: whether another program of the same user can read the Keychain item without the Mac's allow dialog, and whether the shipped signature has the hardened runtime (`codesign -dv --verbose=4`); if either is no, this closes one road of several.
- **Lead 7, the Claude build at each start.** The shell checks the installed build again before each engine start with the install's own check (`codesign --verify --strict`, Anthropic's Team ID and identifier, a Developer ID; `claude_install::cleared`), remembered in memory for one version of the file (inode, size, modification and change times), so it runs once per launch and once per change, about half a second on this Mac. A file that fails is not handed to the engine; Home says calmly that Claude changed and offers Get it again. The engine compares the same version before each Claude start (`sdkEngine.ts resolveClaudeBinary`, `COMPANION_CLAUDE_ID`), so a swap after the check is refused too. Not kept on disk on purpose: a note there could be written by whoever swapped the file. **[verify]** that the installed build's change time does not move in normal use of the shipped app (macOS writing extended attributes, for example), or the engine would refuse it as changed (checked only on a temporary copy with `codesign` and `--version`). Still open: the same Keychain question as lead 1.
- **Lead 6, Google's curl calls.** Every Google request (`google.rs post_form`) starts `/usr/bin/curl` with `-q` first (no settings file is read), https only, and a cleared environment with only `PATH=/usr/bin:/bin` (no `HOME`, `CURL_HOME`, `XDG_CONFIG_HOME` or proxy variables). Still open: a real request on a Mac with a `~/.curlrc` (the tests use a stand in curl that prints what it was given). Not changed: the Dodo license calls (`license.rs`, payments off) already pass `-q` but keep the app's environment (proxy variables reach them; worth the same cleared environment before payments go on); the speech model and Claude downloads (`voice_mac.rs`, `claude_install.rs`) carry no secret.
- **Lead 5, Delete everything and Google.** The wipe helper now revokes each kept refresh token at Google (best effort) and removes every Google Keychain item and the list, just before the Claude key and under the same rule; a failure keeps the key and leaves a note (`google.rs forget_all`, `wipe.rs run_helper`). The Pro trial item is still always kept (T17). The delete list names the Google connections and the privacy policy says so. Still open: one run with a test OAuth client on a throwaway Mac account, since the repo carries no client id.
- **Lead 3, the static server.** The browser check's server for a plain folder (`proof/server.ts serveStatic`) serves only files whose real place, every link followed, is inside the folder or the project (and, for the earlier version's copy, the installed packages, a `node_modules` folder, of the project they are borrowed from; nothing else of that project, since the review of 31 Oct 2026); never a dotfile or a file in a dot folder, by the address or by where a link leads (inside installed packages, `node_modules/.pnpm`, is allowed); and only to a request whose Host is its own `127.0.0.1:<port>` or `localhost:<port>`, so a page that rebinds a name to this Mac gets nothing (`runner/test/audit-static-server.test.ts`). Still open: another macOS account on the same Mac can still reach the port while the check runs (no per run secret in the address; it would change the receipts' addresses).
- **Left open on purpose.** Lead 2 (the OS sandbox and the project's `.companion` folder, `sandbox.ts`) now has a `denyWrite` for `.companion` and `.claude`, still to be checked on a real run (above). Lead 4 (the screenshot drive check accepts any volume named CompanionShots) needs a real Mac to see how the drive is made and found. Leads 8 to 11 are the usage proxy's (abandoned streams booked for input only, client chosen `anthropic-beta` values and unlisted body fields forwarded, plan downgrades not reaching the per token plan copy, the Dodo customer link applying one person's events to another): the proxy is built but not deployed, and F22's switch is off, so they must be settled before that switch is turned on.
