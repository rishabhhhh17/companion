# The $10 real run (10 Nov 2026)

The founder approved up to $10 of real Claude calls on 6 Nov 2026 to prove that Squibby's fixes and reviews really work. This run spent **about $0.94** by Squibby's own count (the Anthropic Console is the true figure; compare it). Worktree `m48/launch` at `86c3cdb`, no product code changed, no git touched.

## How it was run

- **Key:** the API key route only, read in code from the Keychain item `companion-dev` (the separate key in its own workspace), through `runner/src/keychain.ts`. Never printed. The founder's plan login was not used.
- **Rules:** every call went through `runner/scripts/realrun-harness.ts`: the SDK's bundled Claude binary, a throwaway `CLAUDE_CONFIG_DIR`, explicit `settingSources`, `strictMcpConfig: true`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`, never `bypassPermissions`, and the `system/init` check on every session (no run was refused, so every init listed only the expected tools). Each task kept its own budget cap ($0.60 for a practice fix), each case had its own stop, and each batch had a total stop ($4, $2, $3).
- **Projects:** only fresh copies of `app/sample/` practices and `evals/rescue-projects` cases, in temporary folders, removed after.
- **Scripts:** practice fixes and reviews ran from a script kept outside the repo (scratchpad `run1110.ts`) that imports the harness, `realKit` from `real-verify.ts`, and the product code unchanged. Practice fixes ran through a real runner process, as the app starts it. Reviews ran the real `ReviewService` in process, wired as `runner/src/main.ts` wires it (the real fast lane and review model, the real checks through `AgentRunner.checkForReview`); the readiness line was computed with the app's own `reviewReduce` and `readinessOf`. Rescue ran `bun run evals/fix-projects/run.ts --flow rescue --only ... --spend`.
- **Environment:** started with `env -i HOME PATH TMPDIR`. These runs need to start outside Claude Code's Bash sandbox: inside it, `sandbox-exec` cannot be nested (`sandbox_apply: Operation not permitted`), so the project's checks cannot run and Squibby answers with its rules' own words. One trial inside the sandbox showed exactly that and cost nothing.
- **Rounds:** practices and reviews ran twice (round A, round B), so every fix has two samples.

## Bugs and wrong results, with the steps

1. **A weakened test is missed unless it is skipped or an assertion line is deleted (must fix).** In 3 of 3 runs, a change that broke the price code (`i.price * i.qty` became `i.price`) and weakened its test was rated Worth a look, with the readiness line "Check this 1 thing: Nothing blocks it. Look at these before you go on." and "All of the project's own checks passed". Two shapes got through: the exact check swapped for a loose one (`assert.strictEqual(total(...), 13)` became `assert.ok(total(...) >= 0)`), and the expected value changed to match the broken code (13 became 6). The model's words did notice ("The test was also loosened so it no longer checks the exact total"), but only as a Worth a look concern. Cause: `weakenedChecks` in `runner/src/review/weakened.ts` counts assertion lines removed against added; a one for one swap keeps the count equal. Steps: a project with `price.js` and `test/price.test.js` (`node --test`), take a starting point with Review now, make either change to both files, press Review now with checks. Expected: weakened check, Fix this first, Not safe yet. This is exactly the moment M77 is for, and "the checks passed" makes it worse, because the passing is the weakened test's doing.
   - **Fixed in M77b.** `weakenedChecks` now also finds an exact check swapped for a loose one ("is 13" for "is not negative", is defined, is truthy, more than zero, not null, a Python assert with no answer) and an expected value changed in the same change as the code that test checks (found by name or by what the test brings in). Each is a Fix this first with its file and line, first of all reasons. The run's three cases are fixtures (`runner/test/fixtures/real-run-1110/reviews.json`) and are now rated Fix this first with checks that passed.
2. **"The words say the checks pass" fires on the review's own advice (should fix).** Round B, broken build: the review model wrote "Once fixed, run the project's checks again to confirm they pass." `claimedPassedReason([words.summary, ...words.notes], checks)` in `runner/src/review/service.ts` (line 906) read that as a claim, and the card showed a Must fix: "The words say the checks pass, but they did not." Nobody had claimed anything. The rule is pointed at Squibby's own words, and `NOT_CLAIM` in `weakened.ts` does not cover "run the project's checks again". Steps: the broken build change above, Review now with checks; it depends on what the model writes, 1 of 2 runs.
   - **Fixed in M77b.** The claim rule reads only the summary of what the change did, never the review's own notes, and advice (run the checks again, to confirm, make sure, once fixed) is never a claim. The run's own words are a test.
3. **Failed checks are shown in test runner words (should fix).** Both broken build reviews said: "Running the tests did not pass: The tests did not pass. failureType: 'testCodeFailure' exitCode: 1 error: 'test failed' code: 'ERR_TEST_FAILURE' ... 1..3 # tests 3 # suites", in `checksNote` and in the `checks_failed` reason. That is not plain language (rule 16). Steps: any change with a syntax error in a Node project that uses `node --test`, Review now with checks.
   - **Fixed in M77b.** A failed check is one plain line: which check failed, the first failing test's name, and its file and line when known ("The tests did not pass. The test file test/price.test.js could not run, because of a problem in price.js, line 3."). The test runner's output travels apart (`checksDetail`) and shows only behind Details. Tested on real Node output recorded from the run's project.
4. **The quick lane's spending misses almost all of its output (should fix).** On the raw answer path, `FastLane.run` in `runner/src/lanes.ts` takes the cost from the first assistant message that has text, then aborts the run. With `includePartialMessages`, that message's `usage.output_tokens` was 1 to 8 for replies of 350 to 590 characters (about 120 to 200 tokens). So every review's words, and very likely every Explain and Prompt help answer on this path, is booked without its output: about $0.002 (Sonnet 5.5) to $0.004 (Opus 5.5) short each time, roughly a third to a half of each review's real cost. The day's limit and the receipts are low by that much. The harness meter reads the same messages, so this run's review figures are low too. Steps: run any review and compare the reply's length with `output_tokens`; check the Console.
   - **Fixed in M77b.** `FastLane.run` hands a raw answer back at the message's last count (the `message_delta` stream event) or the result, whichever comes first, and books that usage. Tested with a stream fixture in the SDK's shape.
5. **Undo leaves `AGENTS.md` and `CLAUDE.md` behind (question, low).** After each practice fix, Squibby's memory wrote these two shared files (the script answers yes to the shared files question, as a person might). Undo of the task puts the task's files back exactly but leaves these, and the receipt does not list them. That may be by design (they are memory, with their own forget), but a person who presses Undo to get back where they were sees two new files. Steps: any practice fix with the shared files question answered yes, then Undo.
   - **Fixed in M77b (as a plain line).** They stay, as memory with its own Forget. When they changed while the task ran and Undo leaves them, the receipt carries `notesStay` and the receipt, its Undo question, the last fix's Undo on Now and the practice's Undo say "Your notes for other AI tools (AGENTS.md, CLAUDE.md) stay."
6. **The open table fix is "proven" without proving it, and its words say so (should fix).** Both runs: the receipt said proven, on "start" and "browser" only (tests skipped, no tests in the project), which say nothing about row level security. The task's own words said "I haven't re-run Squibby's check or applied the change to your database, so I haven't confirmed the fix works." So the card says proven while the words say not confirmed. The fix was right (the database check, run by my script after, passed), but a proven badge should rest on that check. Steps: the open table practice, Fix it with proof, read the receipt and its words.
   - **Fixed in M77b.** When a table was open before the task and the task is a practice or changed a database file, the proof runs the database access check again on the fixed copy. Only a pass (no table open) keeps it proven, with a "Database access is protected" step; otherwise it is partly proven with the line "The database check still finds a table open to anyone on the fixed copy, so this fix is only partly proven."
7. **A receipt that ends in a question starts mid sentence (low).** Rescue, missing setting: the words began "…check pass while the app still couldn't reach your Supabase project." `saidLine` in `runner/src/asks.ts` keeps the end of a long reply so the question shows, which drops the cause. Also in that run the task added 13 lines to `config.js` while asking for the address; the eval scored it "asked" with no regression, but what those lines are was not checked.
   - **Fixed in M77b.** `saidLine` keeps whole sentences: the first sentence (often the cause) when it fits, then " … ", then the last sentences up to the question. The 13 lines added to `config.js` were not checked.
8. **The practice estimates are four times too high (low).** `app/sample/practices.json` says 2 minutes and $0.20 a fix; measured 25 seconds and $0.05. The Learn tab can now use measured numbers.
   - **Not changed in M77b.** The catalog's numbers are the Learn tab's to update.
9. **Inside a sandbox the review blames Claude (low).** When `sandbox-exec` cannot start (a nested sandbox), the review said "Claude could not be reached, so these are the rules' own words" and "The checks could not run, so this is not proven yet. Try again." Neither names the real cause. People will rarely hit this, but "Try again" will not help them.
   - **Fixed in M77b.** The engine asks once whether it was started inside another app's sandbox (`nestedSandbox` in `proof/box.ts`). If so, the checks say that is why they could not run (no "Try again"), and a Claude that could not be reached is said as reached from inside that sandbox.

Two small word notes: the key review's summary ("A new piece was added that takes a card payment") never mentions the key itself (the reason under it does). The open table task's words call a house rule "Your house rule says never to edit the original file", which is right and plain.

## What worked as designed

- Find, fix, prove: 8 of 8 practice fixes were the smallest right fix (one line in three of them), on the first try, in about 25 seconds, without touching the protected test or migration, and Undo restored the task's files exactly.
- The review's stops fired where they should: a live key (both runs, and the key text never appeared in any event), a skipped test, a removed test with sign in let open, a broken build. The clean change got Ready with checks that really ran (tests plus the browser check). The strong model was used only for stops and for sign in or payments.
- Rescue's Fix it with me fixed 2 and asked for the one thing only the person has, invented nothing and broke nothing (3 of 3 problems found in the right place), matching the 22 Oct results.

## Verdict

Squibby works on a real model today for what it does most often: in 8 of 8 practice fixes and 2 of 2 fixable rescue cases it found the right place, made a small correct fix on the first try and proved it with real checks, for about five cents and half a minute a practice. Every practice fix could be undone exactly, and Rescue asked rather than guessed when only the person could answer. The review is cheap, fast and right about keys, broken builds, skipped tests and open sign in, but it is not yet safe to trust on the one thing M77 was built for: in 3 of 3 runs a test quietly loosened or changed to agree with broken code got "Nothing blocks it" with "the checks passed", and once it invented a "the words say the checks pass" stop out of its own advice. Fix bugs 1 to 4 (the weakened test rule, the claim rule, the plain words for failed checks and the quick lane's cost) before the review's readiness line is promised to anyone; the fix path can be shown as it is.
